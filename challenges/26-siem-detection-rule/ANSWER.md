# Challenge 26 Answer Key — SIEM Detection Rule

**DO NOT READ BEFORE ATTEMPTING THE CHALLENGE**

## Learning Objectives
- Detect credential-theft-style logins, where volume-based thresholds (like challenge 15's) don't apply
- Correlate on *absence* of prior activity and *timing* rather than counting failures
- Recognize that a single-condition rule (e.g. "off-hours only") can still false-positive on legitimate but unusual behavior

## Hints
- A few legitimate users log in from known IPs at odd hours too (on-call
  fixes happen) — "off-hours" alone isn't a safe rule on its own.
- Count how many times each source IP appears *anywhere* in the log, not
  just in successful logins.
- The real incident has zero `Failed password` lines from its IP anywhere —
  the credentials worked on the very first attempt.

## What's planted
`auth.log` is generated by `scripts/generate_auth_log.py` (stdlib-only,
fixed seed 42, deterministic — re-run it from inside `scripts/` and commit
the regenerated `../auth.log` if this challenge ever needs changing) into a
209-line, one-day log with 53 successful logins across 34 distinct source
IPs. It contains five interleaved groups of activity:
- **Known-good internal employees** (12 accounts, `10.0.4.x`): 2-4 clean
  business-hours logins each. Three of them (`mgarcia`/10.0.4.22,
  `drossi`/10.0.4.63, `nkumar`/10.0.4.70) also get one legitimate off-hours
  on-call login — safe distractors, since their IP already recurs elsewhere
  in the log (`count[ip] > 1` excludes them from the real rule).
- **VPN/remote employees** (3 accounts, `172.16.50.x`): 2-3 logins each at a
  mix of business and off-hours times — same safe-because-recurring shape.
- **`twong`** (203.0.113.50, kept verbatim from the original version): 2
  failed attempts (a typo) then 2 successful logins — not an attack.
- **Scanner/bot noise** (13 external IPs): 6-14 failed/invalid-user attempts
  each at common usernames (`root`, `admin`, `test`, `oracle`, `jenkins`,
  etc.), scattered across all 24 hours — none ever succeed. Plus 4 more
  singleton IPs each throwing exactly one invalid-user probe, deliberately
  placed at business hours so they don't collide with the real rule but
  still add "appears exactly once" noise to stress-test it.
- **CRON housekeeping**: hourly `sessionclean` + 4x/day `logrotate` lines,
  irrelevant to SSH auth.
- **The real incident**: `45.33.12.201` — never seen anywhere else in the
  log — logs in as `svc-deploy` at `03:14:22` (off-hours) with **zero**
  preceding failed attempts from that IP. Valid credentials, used correctly,
  on the first try. Unchanged from the original hand-written version.

The trap: filtering on "off-hours login" alone now catches **6** lines, not
just `mgarcia`'s — `nkumar`, `drossi`, `rgarrett`, and `apetrov`'s off-hours
logins are all false positives under that naive rule. The rule needs both
conditions (off-hours **and** source IP never seen elsewhere in the log) to
isolate exactly one line.

## Step-by-step fix
1. `docker compose exec app bash`
2. Count how many times each source IP appears anywhere in the log, then
   cross-reference against successful logins outside 08:00-18:00:
   ```bash
   awk '
     FNR==NR { count[$11]++; next }
     /Accepted password/ {
       ip=$11; user=$9
       split($3, t, ":"); hour = t[1] + 0
       if ((hour < 8 || hour >= 18) && count[ip] == 1) print ip":"user
     }
   ' /var/log/auth.log /var/log/auth.log > /root/alerts.log
   ```
   (The file is read twice via the `FNR==NR` idiom: the first pass builds a
   per-IP occurrence count, the second pass applies the off-hours + first-seen
   filter to `Accepted password` lines.)
3. Confirm `/root/alerts.log` contains exactly `45.33.12.201:svc-deploy`.
