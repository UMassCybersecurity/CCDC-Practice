# Challenge 24 Answer Key — Multi-Source Log Correlation

**DO NOT READ BEFORE ATTEMPTING THE CHALLENGE**

## Learning Objectives
- Correlate web server, application, and authentication logs into a single timeline
- Recognize that an attacker's source IP can change mid-chain once they pivot through a compromised service
- Distinguish an application-layer vulnerability indicator (in `app.log`) from the request that triggered it (in `nginx_access.log`)

## Hints
- Start with `nginx_access.log` and look for a single IP doing recon (404s on `/admin`, `/phpmyadmin`, etc.) immediately before a successful `POST`.
- `app.log` explains *why* that request mattered — grep it for `WARN`/`ERROR`.
- The persistence event in `auth.log` won't come from the attacker's IP — the attacker is pivoting through the web app by then, not SSHing in directly. Look at what's happening a few minutes *after* the exploit, from `localhost`/the web server's own user context.

## What's planted
Three logs generated by `scripts/generate_logs.py` (stdlib-only, fixed seed
24, deterministic — re-run from inside `scripts/` and commit the
regenerated `../logs/*.log` files if this challenge ever needs changing),
all sharing one business day's timeline (Jun 2, 08:00-20:00):

- **`nginx_access.log`** (623 lines): ~16 benign `10.0.5.x` visitors browsing
  normally (products/cart/checkout/static assets), a health-checker hitting
  `/health` every 5 minutes, 6 distinct scanner/bot IPs throwing 404 recon
  bursts at different bad paths (`wp-login.php`, `.env`, `.git/config`,
  `phpmyadmin`, etc.) that never succeed, a few ordinary customer requests
  threaded into the 14:00-14:10 window around the real attack, and the real
  chain from `203.0.113.44` — recon against `/admin`, `/admin/login.php`,
  `/phpmyadmin` (all 404), then `GET /upload.php`, then `POST /upload.php`
  at `14:03:41` which succeeds, then fetching `/uploads/cfg_9f3a.php` with
  `?cmd=` parameters.
- **`app.log`** (271 lines): one INFO line per benign dynamic request plus
  two unrelated decoy WARN/ERROR lines elsewhere in the day (a slow-query
  warning at 09:40, a payment-gateway timeout at 18:05) — neither near the
  attack — and the same real signal as before: a `WARN` at `14:03:41`
  reporting an unauthenticated file write to
  `/var/www/html/uploads/cfg_9f3a.php` because `upload.php` has no auth
  check and no extension allowlist, plus two subsequent `WARN` lines
  flagging unexpected child processes spawned by `www-data`.
- **`auth.log`** (174 lines): 6 named admins with realistic scattered
  sessions, routine legitimate `sudo` commands from those admins (apt
  updates, service restarts — kept well clear of 14:16 so they don't read
  as a second persistence event), 4 scanner IPs throwing failed-password
  bursts across the day, hourly `CRON` logrotate/sessionclean noise, and
  the unchanged real persistence step at `14:16:33` — about 13 minutes
  after the exploit — a `sudo` entry showing `www-data` (the web server's
  own user) appending an SSH key to `/root/.ssh/authorized_keys`. It's
  still the only `authorized_keys` mention in the file, and it doesn't come
  from `203.0.113.44` at all — the attacker is pivoting through the
  already-compromised web app.

Verified programmatically before committing: `203.0.113.44` is the only IP
in `nginx_access.log` with 2+ 404s followed by a POST; the two exploit-time
WARN lines in `app.log` are isolated from the two unrelated decoy
WARN/ERROR lines by many hours; and the `authorized_keys` sudo entry in
`auth.log` is the only one, with nothing else in the `14:1x` window.

## Step-by-step fix
1. `docker compose exec app bash`
2. `awk '{print $1}' /var/log/nginx_access.log | sort -u | while read ip; do echo "$ip: $(grep "^$ip " /var/log/nginx_access.log | grep -c ' 404 ') 404s, $(grep "^$ip " /var/log/nginx_access.log | grep -c POST) posts"; done | grep -v ": 0 404s"` →
   `203.0.113.44` is the only IP doing `/admin`/`/phpmyadmin` recon followed by a
   successful `POST /upload.php` at `14:03:41`.
3. `grep "14:0[2-4]" /var/log/app.log` → the `WARN unauthenticated file write to
   /var/www/html/uploads/cfg_9f3a.php` line at the same timestamp confirms
   `/upload.php` is the exploited endpoint.
4. `grep -A2 -B2 "14:1" /var/log/auth.log` → the `sudo`/`www-data` entry at
   `14:16:33` appending to `/root/.ssh/authorized_keys` is the persistence —
   note it's timestamped a few minutes after the exploit and has nothing to
   do with `203.0.113.44` directly, which is the trap in this challenge.
5. Write to `/root/findings.txt`:
   ```
   IP: 203.0.113.44
   ENDPOINT: /upload.php
   PERSISTENCE: authorized_keys entry appended for root via www-data sudo
   TIME: 02/Jun/2026:14:03:41 +0000
   ```

## Validation
Ran `docker compose up -d --build`, confirmed `docker compose exec app
/scripts/score_me.sh` reported `0 / 4` with no `findings.txt` present. Then:
```
docker compose exec app sh -c 'cat > /root/findings.txt <<EOF
IP: 203.0.113.44
ENDPOINT: /upload.php
PERSISTENCE: authorized_keys entry appended for root via www-data sudo
TIME: 02/Jun/2026:14:03:41 +0000
EOF'
docker compose exec app /scripts/score_me.sh
```
confirmed `4 / 4`. Torn down with `docker compose down -v --rmi local` afterward.
